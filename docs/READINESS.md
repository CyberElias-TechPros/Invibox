## What the original hardening pass corrected

| Area | Previous problem | Implemented behavior |
|---|---|---|
| Invitation privacy | Visibility was not enforced | Non-public event data requires event's guest token; invalid tokens do not fall back to anonymous access; private organizer preview requires authorized session |
| Tenant isolation | Bulk upserts could overwrite another event's IDs | Event-scoped local IDs, conditional upserts and database tenant triggers; invalid batches roll back |
| Concurrency | Autosave could replace RSVP/check-in data | Per-collection versions, mandatory `If-Match`, transactional guards and version reads; explicit conflict handling; CRM updates cannot overwrite existing RSVP/check-in/seating |
| Data lifecycle | Empty schedule deletion did nothing; large deletion lists were inconsistent | Atomic replace semantics with `json_each`; duplicate IDs rejected; empty collections work |
| Authentication | ISO timestamps were compared lexically against SQL timestamps | Julian-date expiry checks for sessions, password reset and team invitations; reset invalidates outstanding reset links and sessions |
| CSRF/abuse | CORS was treated as sufficient protection; rate counters raced | Origin checks, JSON-only writes except uploads, atomic D1 rate counters, body limits, production configuration fail-closed checks, plus optional Turnstile verification with ip_hash logging |
| Roles | Staff check-in routes did not match authorization rules | Exact role/resource rules, financial/contact redaction, role-aware navigation, owner-protected team removal |
| Event lifecycle | Arbitrary transitions and structural live edits | Transition graph, publication needs occasion, live structural locks, completed/archived operational read-only state |
| Dates | Schedule used fixed demo date and UTC+1 | Per-occasion date, event IANA timezone, UTC storage, local display, DST validation and real calendar exports |
| Guest operations | Contact fields ignored; imported guests had no link workflow | Persisted email/E.164 phone, plus-one email/phone/notes, proper CSV quoting/import parsing, formula-safe export, token rotation/revocation, explicit occasion-access editor |
| RSVP | Duplicate keys accepted different bodies; partial updates calculated wrong totals | Payload-bound replay, transaction-safe duplicate handling, lifecycle/deadline checks, duplicate-occasion rejection, plus-one limits, aggregate status from all responses |
| Seating | Capacity check could race | Database-enforced capacity on seating/party-size changes; concurrent assignment tested |
| Guest experience | Any event displayed sample wedding | Actual title, date, location, assigned occasions, RSVP, optional gifting, saved text sections and calendar files; loading/error states never display demo guests |
| Invitation composer | Style controls claimed to save without doing so | Persisted text sections, visibility, ordering, read-only lifecycle state, private preview and publication; cosmetic mock controls replaced; now includes theme presets and localization |
| Communications | Queue enqueue could lose jobs; retries skipped failures; changing audiences skipped recipients | Transactional outbox, five-minute dispatch recovery, frozen recipients, keyset pagination, delivery leases, retry classification, attempt ledger, Resend idempotency keys and explicit retry/history UI; now includes bounce/complaint callbacks, suppression list, List-Unsubscribe headers, scheduled sends |
| Payments | Currency was not verified; webhook receipt could commit before payment state | Reference/amount/currency/status validation; webhook receipt and status update in one transaction; stable paid timestamps; unsupported ticket/asoebi checkout purposes removed; now includes refund/dispute ingestion, settlement ingestion, invoice generation |
| Uploads | Trusted browser MIME declarations | Signature checks, bounded upload requests, authorized retrieval, orphan-object cleanup if metadata insertion fails |
| UI integrity | Global localStorage guest cache and fabricated dashboard values | No persistent organizer PII cache, no automatic demo login, server-derived identity/statistics, visible save failures, honest online-only check-in wording plus offline queue with conflict resolution |
| Delivery | Cross-site cookies could break Vercel → Worker login | Production config generator installs same-origin `/api` reverse proxy; secure cookies remain first-party |

## Supported stories and their order (updated)

1. **Organizer:** register/sign in (optional Turnstile) → request/confirm verification from Account & security (required outside development) → optionally register passkey → create event with date/location/timezone → add public/private occasions → add/import guests with plus-one email/phone/notes → assign private occasion access → edit invitation content with theme presets and localization (en/yo/ig/ha), save drafts offline → preview → publish → distribute individual private links. Publication before schedule fails explicitly.
2. **Guest:** open personalized link → view only assigned occasions → choose each response → optionally add dietary/accessibility notes and companion name within allocation → submit → retry same payload safely. Invalid/revoked tokens expose no event data.
3. **Collaborator:** receive email-bound invitation → register/sign in as invited email → accept before expiry → see role-scoped workspace. Acceptance runs before first-event onboarding. Owner can remove access; admins/owners can revoke pending invitations. Owner can **transfer ownership** to another collaborator via password+MFA and token acceptance.
4. **Event-day staff:** sign in → select assigned event → scan token or search guest → persist check-in online or **offline queue** with device_id and bulk sync (up to 500, last-write-wins) → refresh status. Concurrent repeated scans report existing check-in.
5. **Communications:** configure approved provider and obtain sufficient queued-recipient allowance → enter actual guest contacts → guests opt in through personal invitation → select audience → enqueue transactionally → provider attempts/retries → inspect accepted/failed counts → deliberately retry failures. Delivery-row “sent” means **provider accepted**, not delivered/read; announcement “sent” means processing completed without failures and can include suppressed recipients. UI shows accepted, failed and skipped counts, plus **bounce/complaint suppression** and **List-Unsubscribe** handling. **Scheduled sends** allow future dispatch via cron.
6. **Gifting:** organizer completes bank onboarding, provider verification and operator identity review → enables gifting → guest submits receipt email and amount with persisted intent key → hosted Paystack checkout → verified webhook/status lookup → paid confirmation. Invitation tokens not sent to payment provider in callback URLs. Test flow on same browser; returning in another browser requires original private link. **Refunds** can be requested by owner and approved/processed by admin via Paystack refund API; **disputes** ingested via webhook; **settlements** ingested via cron and linked to payments.
7. **Organizer media:** authorized upload → signature validation → R2 storage → moderation → authorized retrieval. Hosts can enable consent-based guest photo submissions and private, moderated gallery; guest video/audio uploads not supported. Now includes **ticket inventory** with holds and capacity guard, **transport/accommodation/registry/waitlist** management.
8. **Completion:** live structural edits lock → mark completed → review read-only operational records → archive. Owner may export data, erase guest-linked data, or delete archived event without payment records. Financial retention exceptions remain operator-reviewed. **Retention policies** per category configurable by admin and enforced via cron.
